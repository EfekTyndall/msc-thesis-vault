# MSc thesis vault: notes and decisions

Obsidian vault for the MSc thesis (handheld vs VR-teleop demonstrations for GR00T / π0.5). This vault holds the thinking; the sibling repo `msc-thesis` holds LaTeX, analysis, data index and `docs/` (proposal, research notes, thesis plan, hardware specs); `dex1-1-handheld` holds code and CAD documentation (shared with the company at the end, so no vault IDs, vault paths or Claude files there; handover list in `Handover.md`). `Home.md` is the dashboard.

## Layout
- `Literature/@<citekey>.md` from Zotero Integration; citekey = Better BibTeX key in `msc-thesis/thesis/literature.bib`
- `Daily/YYYY-MM-DD.md` daily log
- `Decisions/Dnn <Title>.md` one note per design decision; master copy of each decision's details
- `Experiments/` one note per experiment, linked to `msc-thesis/experiments/<YYYY-MM-DD>-<name>/`
- `Chapters/NN <Title>.md` hub per thesis chapter (`status`: not started / drafting / done)
- `Meetings/YYYY-MM-DD <who>.md`
- `Agent/` machine zone; start with `Agent/Start here.md` (index: live notes, open questions, folder purposes). Folders: `Live/` (notes kept up to date), `Research/` (answers from papers and docs), `Reports/` (what was done or measured), `Explainers/` (visual pages), `External/` (reports for supervisors, external-report skill), `Archive/` (replaced notes, moved not deleted); files named `YYYY-MM-DD <topic>.md`
- `Templates/` Templater syntax (`<% tp.date.now("YYYY-MM-DD") %>`); Literature template is Zotero Integration (Nunjucks)

## Zones
- **Human side** (`Daily`, `Meetings`, `Chapters`, `Literature`, `Decisions`, `Experiments`, `Home.md`): read, link, move, copy. Write or edit only when asked; Decisions only via the `record-decision` skill.
- **Machine side** (`Agent/`): read, write, edit freely. Put research, reports and drafts here, not in human notes. When a note is added to `Agent/`, add its line to `Agent/Start here.md` in the same commit; when a note is replaced, `git mv` it to `Agent/Archive/` and add its "replaced by" row there.
- Never edit `Templates/` or `.obsidian/` unless asked.

## Conventions
- Link notes with wikilinks `[[Note name]]`; refer to repo files as plain text `msc-thesis/<path>`.
- New notes start from the matching template; keep the frontmatter.
- Literature notes: the Annotations section is generated by Zotero; key facts with page numbers go above it.
- Units, terms and writing style as in `msc-thesis/CLAUDE.md` (SI units; third person, technical).
- Codes (decision IDs D01–D10, Replay Ladder phases RL1–RL6, gap IDs such as G8 or A6, conditions C1–C4, options, paths) never stand alone: the first time a code appears in each paragraph, list item or table row, add a short plain-words name, e.g. "RL1 (replay in MuJoCo on the Mac)", "D09 (calibration)".

## How to work
1. Think first: state assumptions; if a request is ambiguous, ask instead of picking.
2. Keep it simple: only what was asked, no speculative features or abstractions.
3. Surgical changes: touch only what the task needs; match existing style; report unrelated issues, don't fix them; never overwrite the user's edits.
4. Goal-driven: define how the result is checked (test, measurement, compile, source) before starting, and run that check before calling it done.
5. Facts only: every number or claim needs a source or a measurement; say "unverified" otherwise.
6. Ask first before: merging, changing a CLAUDE.md or the thesis plan, adding dependencies, or anything that sends messages.
7. Reports: short — what was done, how it was checked, what is open.
8. Research first: before laying out design or decision options, survey how prior work solves the problem (papers in `msc-thesis/thesis/literature.bib`, open hardware, official docs; check `Agent/Start here.md` and `Agent/Research/` first) and tie each option to a source, so the choice can be defended. Say when an option has no precedent. If these are not enough, run a wider search with the `deep-research` skill without asking first (Martyn, 2026-11-24) and say in the result that it was used; sources found that way that are not in the bib are marked "not in bib". Useful sources found that way that are not in the bib are listed at the end of the result under "Add to Zotero" (title, link, why), so Martyn can add them to Zotero and the bib.
9. Before a design or decision answer: (a) state the assumption it rests on and its source in one line ("Assuming X, from note Y"); (b) give at least two options and what decides between them (source, robot observation, practicality), then the recommendation; (c) mark the answer "checked" (source, measurement, robot) or "reasoned only"; reasoned-only answers are checked before they change code, CAD or a procedure. For directions, frames and poses, show the options as a simulation picture first. (Martyn, 2026-11-24)
10. AI use register: when work produces something that may enter the thesis (text, figures, code, analysis, CAD), add or update its row in `Agent/Live/2026-11-24 AI use register.md` (use, sections, own input, tool, remark; plus a P-numbered primary prompt) and in `Agent/Live/2026-11-24 Contributions and own-work table.md` (built / adapted / reused, own work, AI-assisted). Required by the h_da EIT AI rules for the thesis.
11. Notes and replies that ask Martyn to understand or choose something start with a **plain version** before any table: (a) the question and the answer in two sentences; (b) each option walked through on one concrete case (e.g. one recorded take: what runs where, what file comes out), with an everyday analogy where it helps; (c) for each new program, package or format, what it does and why it is needed, in one line; (d) what each option changes for the thesis comparison and what it does not; (e) what the choice depends on, marked checked or unverified. The detailed tables with sources follow. Before posting, check the note answers: what does it do, why is it needed, what changes in practice, when does it matter, does it help the comparison. Thesis text is exempt (stays technical). (Martyn, 2026-11-26)
