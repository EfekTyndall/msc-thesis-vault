# MSc thesis vault: notes and decisions

Obsidian vault for the MSc thesis (handheld vs VR-teleop demonstrations for GR00T / π0.5). This vault holds the thinking; the sibling repo `msc-thesis` holds code, CAD, LaTeX, data index and `docs/` (proposal, research notes, thesis plan).

## Layout
- `Literature/@<citekey>.md` from Zotero Integration; citekey = Better BibTeX key in `msc-thesis/thesis/literature.bib`
- `Daily/YYYY-MM-DD.md` daily log
- `Decisions/Dnn <Title>.md` one note per design decision; master copy of each decision's details
- `Experiments/` one note per experiment, linked to `msc-thesis/experiments/<YYYY-MM-DD>-<name>/`
- `Chapters/NN <Title>.md` hub per thesis chapter
- `Meetings/YYYY-MM-DD <who>.md`
- `Templates/` core Templates plugin syntax (`{{date:YYYY-MM-DD}}`)

## Conventions
- Link notes with wikilinks `[[Note name]]`; refer to repo files as plain text `msc-thesis/<path>`.
- New notes start from the matching template; keep the frontmatter.
- Literature notes: the Annotations section is generated by Zotero; add key facts with page numbers above it.
- Decisions change only via the `record-decision` skill: note, its History, and the decision log in `msc-thesis/docs/thesis-plan.md` §7 stay in step.
- Don't edit existing Daily or Meeting notes unless asked. Never edit `.obsidian/`.
- Units, terms and writing style as in `msc-thesis/CLAUDE.md` (SI units; third person, technical).

## How to work
1. Think first: state assumptions; if a request is ambiguous, ask instead of picking.
2. Keep it simple: only what was asked, no speculative features or abstractions.
3. Surgical changes: touch only what the task needs; match existing style; report unrelated issues, don't fix them; never overwrite the user's edits.
4. Goal-driven: define how the result is checked (test, measurement, compile, source) before starting, and run that check before calling it done.
5. Facts only: every number or claim needs a source or a measurement; say "unverified" otherwise.
