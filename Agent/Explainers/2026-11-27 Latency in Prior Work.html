Latency in Prior Work

How the public code of UMI, DexUMI, ViTaMIn-B and FastUMI measures and removes the delay between camera, pose and gripper. Real code lines from the repositories (read on 27 Nov, none of it run). Charts marked real data use our own desk log of the PICO controller; simulated parts are made up on purpose.

Plain version

The question: a camera image and a hand pose arrive at the recorder late by different amounts. What do the published handheld-gripper projects do about it? The answer: three of the four measure each delay once, store it as a number in a config file, then subtract it from each stream's arrival time and read the pose at the camera frame times. The fourth (FastUMI) measures nothing and takes the nearest pose.

One frame, UMI-style: a frame arrives at 10.000 s. The config says the camera is 0.125 s late, so it was taken at 9.875 s. The pose stream is 0.0001 s late, so a pose that arrived at 9.8751 s was taken at 9.875 s. The pose for the frame is found by a straight line between the two samples around 9.875 s.

Interpolation = finding a value between two samples on a straight line (rotations by Slerp, a turn along the shortest arc). FastUMI skips steps 1 to 3.

3 · How the camera delay is measured: a screen showing the time

UMI, DexUMI and ViTaMIn-B all film a screen that shows the current time as a QR code or an ArUco marker. Delay = arrival time of the frame − the time shown. All the code lines below are from the repositories.

 56 ts_qr = float(code)                                  # time printed in the QR code
 57 ts_recv = data['camera_receive_timestamp']
 58 latency = ts_recv - ts_qr                           # UMI: scripts/calibrate_uvc_camera_latency.py
 82 avg_latency = np.nanmean(qr_det_queue) - np.mean(qr_latency_deque)   # minus the time to draw the QR
107 t_offsets = [v-k-avg_qr_latency for k,v in qr_recv_map.items()]
110 print(f'Capture to receive latency: AVG={avg_latency} STD={std_latency}')

DexUMI (measure_latency.py lines 48–70) does the same with time.monotonic() and prints mean, std, median. ViTaMIn-B (cali_cam_latency.py lines 78–79) uses one frame: video timestamp − ArUco timestamp.

simulated The shown time is only refreshed every few milliseconds, so each frame gives a slightly different answer. The page shows 60 frames of a camera that is truly 125 ms late.

UMI and DexUMI print the mean and standard deviation over many frames; ViTaMIn-B takes one frame. If the shown time is on average half a refresh older than the moment of capture, the result reads high by half a refresh (reasoned only, no repo corrects it).

4 · Gripper and robot: command a motion, compare it with the measured motion

UMI sends the gripper a sine as the width command and records the measured width. It compares the two curves with its own function get_latency. The robot is driven by a spacemouse, and the same function compares commanded and measured pose, one dimension at a time (calibrate_robot_latency.py line 110).

 28 duration = 10.0;  sample_dt = 1 / 100                    # 10 s, 100 samples per second
 32 value = np.sin(sample_t * duration / 1.5) * 0.5 + 0.5
 33 width = value * 80                                       # 0 to 80 mm, about 1 Hz
 58 latency, info = get_latency(x_target=width, t_target=timestamps,
 61                           x_actual=states['gripper_position'],
 62                           t_actual=states['gripper_receive_timestamp'])   # UMI: scripts/calibrate_gripper_latency.py

UMI keeps the delays in config files, not in the recorded data. DexUMI keeps the raw receive times and computes the capture times when processing. Nobody explains where the config numbers came from.

Two gaps. (1) None of the four repositories measures a camera delay from motion; every camera measurement uses a screen with the time on it. (2) For the delay of a VR controller pose there is no code to base a method on. Any method we choose for it is our own and needs its own justification.

What this means for the thesis (recommendation, reasoned from the survey)

A. Follow the references (recommended)

Camera by a screen with the time (needs a screen driven by the recording computer, the Jetson has none now). Robot by commanded vs measured pose (we already have this data from the RL3 replay). Gripper by UMI's sine test at the gripper swap. Then delay file, capture time = arrival − delay, interpolate at frame times. Open: the controller pose delay.

B. Measure nothing (FastUMI)

Nearest pose on one clock. No screen, no tests. The camera delay of about 0.1 s stays inside the data (section 2 shows the size of that error).
