# GR00T and π0.5 action format for handheld data

Question (Martyn, 2026-11-18): for the handheld recordings, should training data be absolute end-effector poses in the robot base (needs a room → base calibration each session) or relative actions (UMI-style)? Which do GR00T and π0.5 expect? Follows [[2026-11-17 Controller pose to robot frame]].

Method: source read of [Isaac-GR00T @ 708617f](https://github.com/NVIDIA/Isaac-GR00T/tree/708617f) (GR00T N1.7, 2026-11-17) and [openpi @ 215abfb](https://github.com/Physical-Intelligence/openpi/tree/215abfb) (π0 / π0.5 code, 2026-08-24). No paper in `msc-thesis/thesis/literature.bib` covers GR00T or π0.5 action formats. Nothing was run.

## Short answer

- **Both models take absolute poses in the dataset and turn them into relative actions themselves**, during training, using the current robot state. Gripper stays absolute in both. So the current export convention (absolute position + 6D rotation + gripper width, LeRobot v2) fits both; the relative/absolute choice is a **fine-tuning setting**, not a recording or export choice.
- **GR00T N1.7**: relative end-effector actions are the recommended default. Computed as `T_state⁻¹ · T_action`, i.e. in the gripper's own frame. The room → base offset and rotation cancel in the action.
- **π0.5 (openpi)**: relative ("delta") actions are `action − state`, number by number. The position offset cancels, but the axis directions (heading) of the frame do not.
- **Catch for both**: the model also gets the *current absolute pose* as state input. If training state is in the room frame and the robot state at deployment is in the base frame, they do not match. So a room → base calibration (or at least heading alignment) is still needed unless the state input is left out or made relative. Not checked whether either code base supports that cleanly.

## What this means for the handheld

1. **Recording / export: no change.** Keep absolute pose (position + 6D rotation) + gripper width at 30 Hz, as in `msc-thesis/CLAUDE.md`. Both models can make relative actions from it.
2. **Frame of the export** is the open point. The actions become frame-free in GR00T (gripper-frame relative), but the absolute *state* input is not. Options, each with a source:
   - (a) Calibrate room → base each session and export in the base frame (li2025 hand-eye on the arm; zeng2025 docking jig). Same frame as the robot at deployment.
   - (b) Leave the absolute state input out or make it relative too (UMI, chi2024, uses relative proprioception). Support for this in GR00T / openpi configs: not checked.
3. The VR teleop data are recorded on the robot, so they are in the base frame already; this question only concerns the handheld data.

## Follow-up 2026-11-18: can the pose state be left out? (option B, [[D07 Software and data format]])

- **GR00T N1.7: yes, built in.** Model config `exclude_state` ("Zero out all state inputs") feeds zeros as state to the model; the state is still read to convert absolute actions to relative ([gr00t_n1d7.py L128–129](https://github.com/NVIDIA/Isaac-GR00T/blob/708617f/gr00t/configs/model/gr00t_n1d7.py#L128-L129), [processing_gr00t_n1d7.py L500–512, L678–693](https://github.com/NVIDIA/Isaac-GR00T/blob/708617f/gr00t/model/gr00t_n1d7/processing_gr00t_n1d7.py#L678-L693)). The per-embodiment state config can also set it. Separately, `state_dropout_prob` randomly zeroes state during training (fine-tune default 0.2, model default 0.8; [README L508](https://github.com/NVIDIA/Isaac-GR00T/blob/708617f/README.md#L508)). So: export absolute poses, relative EEF actions, `exclude_state` on → the absolute (frame-dependent) pose never reaches the model.
- **openpi (π0.5): no flag, but possible with own transform.** The model input `state` is whatever the user's `Inputs` transform puts there (LIBERO example maps `observation/state` → `state`, [libero_policy.py L57](https://github.com/Physical-Intelligence/openpi/blob/215abfb/src/openpi/policies/libero_policy.py#L57)); π0.5 puts state into the language tokens (`discrete_state_input`, [pi0_config.py L29–41](https://github.com/Physical-Intelligence/openpi/blob/215abfb/src/openpi/models/pi0_config.py#L29-L41)). `DeltaActions` subtracts that same state, so with zero state it must not be used; instead the actions are made relative (gripper frame) in our own transform or export, and state set to zeros or a relative value. Not tried; effect on π0.5 quality unverified.
