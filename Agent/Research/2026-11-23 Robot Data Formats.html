Robot Data Formats

Which file formats robot-learning projects use to store demonstrations, what each one looks like inside, and why this thesis records in MCAP and trains from LeRobot.

Sources are linked in each section. Papers not in the thesis bibliography are marked not in bib. Own arithmetic is marked computed; anything not checked is marked unverified.

Words used on this page

Format: the rule for how bytes are laid out in a file, so another program can read them back.
Stream (also topic or channel): one sensor's sequence of messages, e.g. camera images.
Timestamp: the time attached to one message. ns = nanoseconds.
Episode: one demonstration, from start to stop.
Chunk: a block of data stored together, often compressed, that a reader can jump to directly.
Index: a table in the file that says where each chunk or message sits.
Schema: the list of a message's fields, with names and types.
Compression: shrinking data. Lossless gets every bit back; lossy (video) drops some detail.

The big picture

Two jobs, two kinds of format

Demonstration data passes through two stages. Recording formats (log formats) write every sensor as it arrives, at its own rate, without losing data if the computer stops. Training formats (dataset formats) hand a training program episodes already cut into equal time steps, for fast random reading.

Between the two sits alignment: each stream's delay is subtracted, and pose and gripper width are interpolated at the camera frame times (UMI, chi2024 PD1.1; ViTaMIn-B, li2025 IV-B).

Some projects skip stage 1 and write the training format directly while recording, e.g. FastUMI writes HDF5 from a ROS node, keeping only the nearest pose per frame (zhaxizhuoma2025 III-A). The alignment is then fixed forever.

Recording format

MCAP .mcap

One file, many streams. The file is a list of records: a Schema describes a message type, a Channel names one stream and points to its schema, a Message is one timestamped sample. Messages are packed into compressed chunks; an index at the end lets a reader jump to any time or stream.

Strengths

  • Every message keeps two original timestamps, "recorded" and "published", in ns (spec).
  • "Append-only design to … reduce the risk of data corruption during unclean shutdowns" (mcap.dev).
  • Schemas stored in the file, so it stays readable "even as your codebase evolves"; any encoding: Protobuf, ROS, JSON and more (mcap.dev).
  • Compressed chunks stay indexed (spec).

Weaknesses

  • No notion of episodes or equal time steps: a conversion step is always needed before training.
  • No direct MCAP reader found in the GR00T, openpi or LeRobot READMEs (unverified beyond those).
  • Fewer robot-learning papers use it than HDF5.

Who uses it: ROS 2, where it is "the default log format" (mcap.dev), since the Iron release (ROS 2 Iron notes). RAPID records MCAP with nanosecond timestamps (yin2026, App. A and D; from a summary, check in the PDF before citing). Viewer: Foxglove.

Recording format

ROS bags .bag · .db3

ROS (Robot Operating System) is the common robot software framework. Its recorder, rosbag, saves every topic to a "bag". ROS 1 used its own .bag format with chunks, compression and an index (ROS wiki, bag format 2.0). Early ROS 2 stored bags as a SQLite database (.db3), one table row per message.

ROS 2 dropped SQLite as default in the Iron release: "in many cases this was not performant enough and lacked certain features desirable for offline processing", so the new default became MCAP, a format "influenced by the original ROS 1 bag file format" (ROS 2 Iron notes). rosbag2's own compression makes files no longer indexable, while MCAP's chunk compression keeps the index (rosbag2 README).

Relevance here: the thesis stack uses no ROS 2 (Replay Ladder plan, 2026-11-20), so bags matter only as background for why MCAP exists.

Training format · sometimes recording

HDF5 .hdf5 · .h5

A small file system inside one file. Groups act as folders, datasets are arrays of numbers (a table, a stack of images), and attributes are name–value labels on either. Datasets can be chunked and compressed (HDF Group intro). Each project picks its own folder layout; two common ones:

Strengths

  • One file, mature tools, fast slicing of arrays.
  • The most common choice in imitation-learning code (ACT, robomimic; FastUMI and RoboManipBaselines in the bib).

Weaknesses

  • No official guarantee that a file left open survives a crash; corruption after crashes is reported (HDF forum).
  • Live-reading mode (SWMR) cannot append variable-length data (HDF Group).
  • Streams at different rates need a self-made layout.
  • Raw images are large: one 640×480 colour frame = 921,600 bytes, ≈ 27.6 MB/s per camera at 30 Hz (computed).

Who uses it: FastUMI, written by a ROS storage node at record time (zhaxizhuoma2025 III-A); RoboManipBaselines, HDF5 plus MP4 per episode (murooka2026 IV-B); ACT and robomimic (not in bib).

Training format

Zarr .zarr · .zarr.zip

Like HDF5 (groups of arrays), but each array is cut into chunks and every chunk is stored as its own small object: a file in a folder, an entry in a zip, or an object in cloud storage. Zarr is "a powerful library for storage of n-dimensional arrays, supporting chunking, compression, and various backends" (Zarr docs).

UMI and Diffusion Policy use it as a replay buffer: all episodes are glued end to end in one long array per field, and a small list, episode_ends, says where each episode stops.

Strengths

  • Chunks can be read in parallel; storage on disk "as a nested directory … or a zip file" (Diffusion Policy README, not in bib).
  • Very simple layout; whole dataset can sit in memory for fast training.

Weaknesses

  • In robotics, tied to the Diffusion Policy and UMI code; GR00T and openpi read LeRobot instead (see below).
  • Holds already-aligned steps; raw timing is gone.

Who uses it: UMI (chi2024): its pipeline ends with 07_generate_replay_buffer.py -o dataset.zarr.zip and training reads that file (UMI README). Diffusion Policy (not in bib).

Training format · the thesis export

LeRobot dataset Parquet + MP4

A folder, not a single file. Numbers per time step (state, action, timestamp) go into Parquet tables, a column-based table format. Camera images go into MP4 videos, which are much smaller than raw frames. A meta/ folder describes features, frame rate, tasks and per-episode statistics. When training, frames are decoded from the video "to be synchronous with data from parquet files" (LeRobot source).

Strengths

  • Input format of both target models: openpi "Convert your data to a LeRobot dataset (which we use for training)" (openpi README); GR00T as above.
  • Video keeps image data small; Hub hosting, streaming during training and a web viewer (LeRobot v3 docs).

Weaknesses

  • Video compression is lossy, so frames are not bit-exact (codec settings not checked, unverified).
  • Versions change: LeRobot main is v3.0 and ships a v2.1 → v3.0 converter, but GR00T expects v2.
  • Holds aligned steps only; raw timing is gone.

Who uses it: openpi (π0, π0.5), Isaac GR00T, Hugging Face LeRobot policies, Grabette: "the output is a standard LeRobot dataset" (Grabette blog, not in bib).

Training format

RLDS TFRecord

Google's shared layout for robot and reinforcement-learning data, built on TensorFlow Datasets. A dataset is a list of episodes; each episode holds a list of steps; each step holds an observation, an action, a reward and flags that mark the first and last step (RLDS README). On disk these are TFRecord files.

Strengths

  • One layout across many labs: Open X-Embodiment pools "1M+ real robot trajectories spanning 22 robot embodiments" (OXE site, not in bib), each "represented using the RLDS episode format" (OXE repo).

Weaknesses

  • Tied to TensorFlow tools.
  • Not read by the thesis models: openpi's own example takes LIBERO data in RLDS and converts it to LeRobot first (openpi README).

Who uses it: Open X-Embodiment and the large shared datasets built on it (not in bib).

The thesis choice (Martyn, 2026-11-23)

Record MCAP, align offline, export LeRobot

  1. Record raw in MCAP. Camera, controller pose, trigger and gripper arrive at different rates and with different delays. MCAP keeps every message with its own ns timestamps (spec) and is built to survive an abrupt stop (mcap.dev). Precedent: RAPID (yin2026). Already in the approved proposal (msc-thesis/docs/proposal.md, sections 6–7).
  2. Align offline. Stream delays are measured at RL5 (camera and recorder test on the station Jetson) and again at RL6 (Dex1-1 gripper and camera swap). Raw data lets old recordings be re-aligned with the new numbers. Method from UMI (chi2024 PD1.1) and ViTaMIn-B (li2025 IV-B). FastUMI stores only aligned pairs (zhaxizhuoma2025 III-A), so it cannot re-align.
  3. Export to LeRobot. The one format both target models read: openpi and GR00T (READMEs above). Zarr or RLDS would need a second conversion. Matches D07 (software and data format).

Still open. Which LeRobot version to write: GR00T wants a v2 flavour plus modality.json, LeRobot main writes v3.0, and the version openpi's pinned LeRobot commit reads is unverified. Video codec loss in the export is unchecked.
